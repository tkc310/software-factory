# 指摘の記録と昇格

エージェントや人のレビューで見つかった誤りを記録し、繰り返すものを機械的なルールに変える。

## 運用ルール

1. 誤りを見つけたら下の表に 1 行追加する。既に同じ種類の行があれば「回数」を増やす。会話で人から受けた訂正も記録する。秘密情報や個人情報は書かない。
2. **回数が 2 になったら昇格を検討する**。データを失う・壊す誤りとセキュリティの誤りは、回数が 1 でも検討する。優先順位:
   0. 設計でなくす(状態の持ち主を 1 つにする、正しいやり方を 1 つにする、手で同期している一覧を 1 つの正本にする、まねされる古いやり方を消す)
   1. 型(ブランド型、スキーマ、判別可能なユニオンで不正な状態を表せなくする。対応表は `Record<型, …>` で持たせ、項目の書き漏れを型で見つける)
   2. 依存ルール(`.dependency-cruiser.cjs`)
   3. lint ルール(`.oxlintrc.json`)
   4. テスト(失敗を再現するテストを追加)
   5. フック(`.claude/settings.json`、`.cursor/hooks.json`、`lefthook.yml`)
   6. どれも無理なときだけ `AGENTS.md` に文章で追記
3. 昇格したら「昇格先」に仕組みとファイルを書き、状態を「昇格済み」にする。昇格した規則が、記録した誤りで実際に失敗することを確かめる。独自の検査のエラーメッセージには、代わりに使うものを書く。
4. 構造で止められたら、同じ内容の文章を `AGENTS.md` や規約に残さない。
5. 原因が知識の不足(仕様や ADR に無い)なら規則を足さず文書を足し、ルールが曖昧なら足さずに書き直す。
6. 構成そのものの問題(層が足りない/多すぎる)が原因なら、ADR の見直しを提案する。

## 記録

| ID | 日付 | 種類 | 内容(何が起きたか) | 回数 | 状態 | 昇格先 |
| --- | --- | --- | --- | --- | --- | --- |
| L-001 | [YYYY-MM-DD] | 境界違反 | [記入例: features/a が features/b の内部関数を import した。実際の記録を足したらこの行を消す] | 1 | 記録のみ | — |

種類の例: 境界違反、型の抜け道、検証漏れ、テスト不足、不要な抽象化、依存の追加、手順の省略

## ルールと強制手段の対応表

ルールごとに、それを強制しているものを書く。強制手段が「なし」のルールは、再発したら昇格の候補にする。強制できるようになったルールは、文章から消す。

| ルール | 強制しているもの | 根拠(LESSONS の ID、ADR) | 追加した日 |
| --- | --- | --- | --- |
| [記入例: feature の内部を他の feature から import しない] | [依存ルール `no-feature-internals`] | [ARCHITECTURE.md] | [YYYY-MM-DD] |
| [記入例: 名前は feature の README の用語に従う] | なし(判断が要る) | | |
