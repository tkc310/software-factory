$ARGUMENTS を、利用者と同じ経路で動かして確かめます。

## 起動

- 起動のコマンド: `[make dev-verify など。空のデータから、マイグレーションと初期データを含めて使える状態にするもの]`
- 使える状態になったことの見分け方: `[例: http://localhost:[ポート]/health が 200 を返す]`
- 並べて起動できるか: [できる(ポートを環境変数で変える)/ できない]

## 診断

操作してよいかを、読み取りだけで確かめる。

- `[例: curl -fsS http://localhost:[ポート]/health]`
- 自分が起動したものでなければ、操作しない。

## 操作

- 使う道具: `[例: Playwright の CLI、scripts/verify/drive.ts]`。毎回書き直さず、同じドライバーを再利用する。
- 何をどう操作するかは、対象の feature の README と仕様の受け入れ条件に従う。
- セレクターは、ロール、ラベル、`data-testid` を使う。座標や CSS のクラスは使わない。

## 証拠

- 置き場所: `[例: .verify/<日時>/。Git の対象外にする]`
- 記録するもの:
  - 操作の前後の画面(スクリーンショットか動画)
  - 操作の結果の状態(画面の表示、API の応答)
  - 副作用(書かれたファイル、追加された行、送られたメッセージ)
- PR の説明の「確かめたこと」に、実行したコマンドと証拠の場所を書く。

## 後片付け

- 自分が起動したものだけを止める: `[例: make dev-verify-stop]`
- 証拠は消さない。

## 守ること

- 前提が足りず確かめられないときは、失敗として報告する。手順を弱めて通さない。
- 確かめていないことは「未確認」と書く。
- 製品の不具合を見つけたら、このスキルや仕様を書き換えて隠さず、報告する。
