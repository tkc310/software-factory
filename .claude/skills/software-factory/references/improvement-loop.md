# 改善ループ

工場は、自分の失敗から規則を足して良くなる。改善は二つの周期で回す。

| 周期 | 担当 | 入力 | 出力 |
| --- | --- | --- | --- |
| PR ごと | `retro` エージェント(`/retro`) | PR、レビューの指摘、その PR の CI の失敗 | 同じ PR に含める `docs/feedback/LESSONS.md` への追記 |
| 会話のたび | 訂正を受けたエージェント | 人からの訂正、指摘 | `docs/feedback/LESSONS.md` への追記(その作業の PR に含める) |
| 週ごと | 改善ジョブ(形式 A: `factory-improve.yml`、形式 B: ルーティン `factory-improve`) | 直近 1 週間の LESSONS.md の追記、CI の失敗、PR のレビューコメント、ラベル `improvement` の Issue | 規則を昇格させる下書き PR と、週次の報告 |

## PR ごとの振り返り

**必須**

- マージの前に、PR のブランチで `/retro <PR 番号>` を実行し、記録を同じ PR に含める。
- 記録するのは、**仕組みで防げたはずの誤り**だけにする。例: レビューで指摘された境界違反、CI で初めて見つかった型の抜け道、仕様にない変更、同じ質問の繰り返し。
- 既に同じ種類の記録があれば、新しい行を足さず回数を増やす。
  - 理由: 回数が昇格の判断材料になる。
- 会話で人から訂正や指摘を受けたときも、同じ形で記録する。PR のレビューを経ない誤りは、記録しないと週次の改善に届かない。
- 記録に、秘密情報や個人情報を書かない。

## 改善の入口

**推奨**

- 使っていて気づいた不便や不具合は、Issue テンプレート「改善提案」(`.github/ISSUE_TEMPLATE/improvement.yml`、ラベル `improvement`)で起票する。種類(データを失う・壊す、設計のルールの破れ、成果物の品質、開発体験、見た目の好み)を選ばせ、優先度の判断に使う。
- 週次の改善ジョブは、開いている `improvement` の Issue も集める。直した PR は Issue を閉じ、LESSONS.md に記録する。

## 週ごとの改善

**必須**

- 週に一度、改善ジョブを動かす。形式 A は `templates/github/workflows/factory-improve.yml`、形式 B は `templates/routines/weekly-improve.prompt.md` のルーティン。どちらも手動でも起動できる(Actions の workflow_dispatch、ルーティンの Run now)。
- 改善ジョブは次を集める。
  - LESSONS.md のうち、回数が 2 以上で、状態が「記録のみ」の行
  - 直近 1 週間に失敗した CI のジョブと、失敗したステップ(どの規則で落ちたか)
  - 直近 1 週間にマージされた PR のレビューコメントのうち、必須の指摘
- 集めたものから、昇格の候補を選び、規則を変更する**下書き PR**を作る。昇格の優先順位は LESSONS.md の運用ルールに従う(設計でなくす → 型 → 依存ルール → lint → テスト → フック → 文章)。
- 候補は、原因で扱いを分ける。ルールを足すのは、原因が「強制されていない」ときだけにする。

  | 原因 | 扱い |
  | --- | --- |
  | 知識の不足(仕様、ADR、feature の README、用語が無いか見つけにくい) | ルールを足さず、文書を足す |
  | 既存のルールが曖昧、または矛盾している | 新しく足さず、書き直す |
  | ガードレールの誤検知、強すぎる制約(正しい変更が止められた) | 緩める変更なので、Issue で人に問う |
  | 検証の仕組みの問題(遅い、結果が揺れる) | 仕組みを直す |
  | ルールはあるが強制されていない | 強制する仕組みに昇格する |

- 回数が 1 でも、データを失う・壊す誤りと、セキュリティの誤りは昇格の候補にする。それ以外の 1 回きりの事例は、規則にしない。
  - 理由: 1 回きりの変わった事例から規則を作ると、規則が増えるだけで誤りは減らない。
- 週次の報告を Issue に書く: 集計の結果、選んだ候補と理由、選ばなかった候補と理由。
- 改善の PR は人がレビューしてマージする。改善ジョブは PR をマージしない。

## 自己改善の歯止め

改善ジョブとエージェントは、ガードレールを**強める**変更だけを提案できる。

**必須**

- 規則を緩める変更(lint ルールの無効化、依存ルールの例外、権限の許可の追加、保護パスの削除)は、改善ジョブが自分で提案しない。必要と判断したら、PR ではなく Issue で人に問う。
- ガードレールの設定ファイルは保護パスなので、改善の PR は CODEOWNERS の承認を必須にする。
- 一つの PR で変える規則は、一つの種類の誤りに対するものに限る。
  - 理由: 規則の効果と副作用を、誤りの種類ごとに追える。
- 1 回の週次の改善で作る PR は 3 本までにする。
- 改善ジョブとエージェントは、自分が作った規則の変更を自分で合格と判定しない。判定は CI と人が行う。
- ルールやスキルの不具合に別の作業の途中で気づいたら、その作業には混ぜず、記録して別の PR にする。
  - 理由: 機能の変更に混ざると、規則の変更として確かめることも、効果を測ることもできない。
- 指標を良く見せるための変更(テストを弱める、失敗を記録しない、検査を外す)は、緩める変更として扱う。
- 動かさずに読むだけのエージェントのレビューを、何度も重ねない。確かめるのは、検査の実行の結果で行う。
  - 理由: 目的を知らない確認役は重要でない点を拾いやすく、書き手はそれを考えずに受け入れやすい。

**推奨**

- 次のどれかが起きたら、改善ジョブを止め、人がループの設定を見直す: 再発の数が増えた、誤検知が増えた、CI の実行時間が大きく伸びた、人の承認の負担が増えた。

## 構造で直したら、文章を消す

**必須**

- 誤りを設計、型、依存ルール、lint、テストで止められたら、同じ内容の文章の指示を AGENTS.md や規約に足さない。すでに文章があれば、同じ PR で消す。
  - 理由: 文章のルールは守られなくても何も失敗しない。強制された内容まで文章に残すと、ルールファイルが長くなり、強制されていないルールが埋もれる。
- 構造にできない教訓だけを文章にする。そのときは、失敗の例を添える。

## 規則の効き目の確認

**必須**

- 昇格した規則には、その誤りを再現するファイルやテストを付け、規則が実際に止めることを示す(依存ルールなら違反する import、lint なら違反するコード)。できれば、記録された実際の誤りを使う。
  - 理由: 失敗するところを見たことがない検査は、何も証明していない。
- 正しく通るべき変更が止められないことも確かめる(既存のコードで `make check` が通る)。
- 独自の検査を足すときは、エラーメッセージに、代わりに使うファイル、型、関数を書く。
  - 理由: エージェントはエラーメッセージを読んで直す。代わりが書かれていないと、検査を避ける書き方を探し始める。

**推奨**

- 昇格から 4 週間、同じ種類の誤りが記録されないかを週次の報告で確認する。再発したら、規則の穴を記録する。
- 検査を足した PR では、CI の実行時間への影響を書く。

## 棚卸し

**推奨**

- 月に一度、週次の報告で次を人に示す。削除は緩める変更なので、人が決める。
  - LESSONS.md の「ルールと強制手段の対応表」で、強制手段が「なし」のルールの数と、その推移
  - 4 週間以上一度も発火していない、または他と重複・矛盾している規則
  - 強制手段ができて、文章が要らなくなったルール

## 指標

**推奨**

週次の報告で、次を前の週と比べる。目標値は仮に置き、実測してから見直す。

| 見たいこと | 指標 |
| --- | --- |
| 再発していないか | 同じ種類の誤りの再発数、人が同じ訂正を繰り返した回数 |
| 早く見つかっているか | 誤りが見つかった場所の内訳(手元のフック、CI、エージェントのレビュー、人のレビュー、マージ後) |
| 構造に落ちているか | 昇格先の内訳(設計、型、依存ルール、lint、テスト、フック、文章)、強制手段のないルールの数 |
| ガードレールの質 | 誤検知の数、lint の無効化と例外の数、結果が揺れるテストの数、CI の実行時間 |

## スキル自体への還元

対象リポジトリで昇格した規則のうち、他の案件でも使えるものは、このスキルと architecture-selection の `FEEDBACK.md` に記録し、雛形に取り込む提案をする。
